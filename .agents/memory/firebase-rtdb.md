---
name: Firebase Realtime Database backend
description: How the API server persists data in Firebase Realtime Database and how numeric IDs are maintained.
---

The API server stores all data in Firebase Realtime Database instead of the original PostgreSQL/Drizzle stack.

- **Database URL:** `https://kingsmm-dab0e-default-rtdb.firebaseio.com` (also set as the `FIREBASE_DATABASE_URL` env var).
- **SDK:** The `firebase` npm package is used server-side, importing from `firebase/database` (`getDatabase`, `ref`, `get`, `set`, `update`, `remove`, `runTransaction`).
- **Collections/paths:** `users`, `wallets`, `services`, `orders`, `topupRequests`, `settings`, `sessions`, `counters`.
- **Numeric IDs:** Services, orders, and topup requests use string keys like `"1"`, `"2"`, etc. The next number is generated by a `runTransaction` on `counters/{services|orders|topupRequests}` so the frontend and admin panel continue to see integer-like IDs.
- **Dates:** Stored as ISO strings on write and parsed back to `Date` on read.
- **Workflows:** The legacy non-artifact `API Server` and `King SMM` workflows were removed. The canonical dev workflows are the artifact-managed ones: `artifacts/api-server: API Server` and `artifacts/king-smm: web`.

**Why:** The original Firebase project had Firestore billing disabled, so the app was switched to the Realtime Database instance provided by the user.

**How to apply:** Keep the existing API layer in `artifacts/api-server/src/lib/firestore.ts` but update it if new collections or queries are added. For any new collection that needs numeric IDs, add a `counters/{collectionName}` node and use `runTransaction` the same way as `services`, `orders`, and `topupRequests`.
